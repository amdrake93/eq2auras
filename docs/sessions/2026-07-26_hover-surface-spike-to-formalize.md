# Session chronicle — the hover surface: spike to formalization

*2026-07-23 → 26. Goal: the mouseover/hover UI surface — the drill-down seam the meter reserved as a **mouseover**, not an in-view toggle. Ran a new **spike mode** end to end: build the UI capability first (Alex's long-standing "build the hover surface, then feed data into it"), field-iterate it live on `dev-latest` — published **manually, without touching `main`** — until the feel settled, then formalize the settled shape into a reviewed feature (spec → plan → implement → merge). Ended on `dev-latest 1.1.38`, `stable` untouched at 1.1.0. Stories worth keeping: how a fourth workflow gear got named; the manual-publish trick that kept `main` clean for a throwaway; "it's just always in the way" and the tooltip that dissolved it; a stale-frame bug that survived a wrong fix before systematic-debugging found the root; Alex's placement vision; and the formalization's "this seems backwards," where Core stopped being the brain and became a passive helper.*

## Spike mode — a fourth gear

We had three named workflow modes (fix-flow / per-gate-review / full-autonomous). This session added a fourth. When I proposed "spike mode," Alex's reply was just *"uh sure, spike mode is new"* — a flag, not a rejection, so I pinned it before building: a **spike** is an exploratory, throwaway-friendly build — branch, **no spec/plan/reviewer** — where the open questions (here, WPF UX feel: placement, occlusion, latency) only have answers once it's in his hands, and WPF is unverifiable on the Mac so his box *is* the test loop. The obligation it carries: once the shape settles, **formalize** — a real spec + reviewed implementation — so the reusable primitive gets its review before it's load-bearing. Spike buys speed on the *learning*, not a pass on the *rigor*.

The load-bearing constraint Alex attached: any expedient data/plumbing a spike does carries **zero design weight**. When the real thing is later designed, it starts from a blank page — "the POC already did it this way" is never an argument. He said it plainly when he agreed to wire real data into the POC: *"i just dont want it to have any sway over the actual brainstorming and designing of the data pipes we end up with."* That single rule shaped everything downstream — and it's exactly why the formalization deleted the spike's data path rather than inheriting it.

## Publishing to `dev-latest` without touching `main`

A spike wants the field-test loop but not a throwaway commit on `main`. Alex asked the right question — *"do we have an easy way to push a dev latest without merging to main? maybe a bit manual"* — and there was. The self-updater pulls the `dev-latest` GitHub release by tag and installs on **release-name inequality** (identity, never ordering — `SelfUpdater.cs`/`UpdateDecision.cs`). CI only *automates* the publish from `main`; the release itself is just a DLL asset + a name. So the manual loop each iteration: back up the current asset, download the branch's CI-built artifact (exact bytes), `gh release upload dev-latest --clobber`, `gh release edit --title <version>`. Alex checks for updates, the name differs, he pulls it. `main` stayed clean the whole spike (the one guardrail: don't push `main` while the manual build is live, or CI would republish over it — it never did).

This is worth remembering as a general capability: **the dev channel can be driven by hand**, decoupled from `main`, for exactly this kind of throwaway iteration.

## "It's just always in the way"

The first real design beat was gesture coexistence, and Alex talked himself into a corner live: the popup renders anchored to the row, but to left/right-click the row your cursor is *on* the row, which is where the popup is… *"oh. its just always in the way."* The exit was to reject the premise: a hover surface doesn't have to be a **menu** you move into — it's a **tooltip**. Make it hit-test-transparent (`ClickThrough.Set` + `IsHitTestVisible=false`) and offset, and the cursor never enters it; "leave the popup to click" isn't a transition that exists. That one reframe — *tooltip, not menu* — is the whole interaction model, and it's what makes the click-through gestures coexist for free.

## Feasibility: decompile first, don't remember

Before committing the POC to any data shape, Alex wanted feasibility settled — and specifically wanted the *actual* current binary, not our stored model. So we fetched ACT **3.8.5.288** exactly as CI does and decompiled it fresh (it matched our doc, but the re-derivation was the point). The finding that unlocked everything: ACT groups swings by `(category → ability)`, **not** by target — but every retained `MasterSwing` carries `Victim` and `Attacker`, so per-target/per-source is **derivable** by iterating a bucket's swings under the lock, the same deep-read shape the recap and drill already use. Four consumer shapes fell out (DPS-list by-target, drill by-ability-by-target, death-list by-source, recap-second events); the first three feed the existing `BreakdownEngine`, the fourth is an event list. Alex's constraint made the cost model easy: a mouseover is a deliberate act (the cursor has left combat), so the read can be lazy/on-demand — feasibility, not per-tick cost, was the only question, and it was a yes.

## The field-iteration ladder — and the one real bug

The spike shipped as a ladder of builds, each a reaction to Alex on the box: `1.1.31` POC → `.32` screen-bounds-aware placement (borrow the grid's `SystemParameters.PrimaryScreen*`, flip left/right on overflow — his meters live lower-right) → `.33` a hide-on-row-change guard → `.34` the stale-frame fix → `.35` dynamic width to fit the data → `.36` distinct floating-card styling (the popup was wearing identical meter chrome and vanishing into the neighbouring HPS meter — a screenshot made it obvious) → `.37` row-anchored placement → `.38` default-left → `.39` bottom-row alignment → `.40` grow-up/grow-down + header-height match. Most were taste/polish. One was a genuine bug.

## The stale-frame bug — a wrong fix before the root

Alex: *"we seem to be rendering the window before data is ready, showing previous data in a new window. Very disorienting."* My first fix guessed at the lifecycle — hide the popup on hover-in to a new row. It didn't work, and that failure was the signal to stop guessing. Under `systematic-debugging`, the root cause: the popup window was **reused** (`Hide()`, not destroyed), and a hidden WPF window **retains its composited visual** — so the next `Show()` flashed the *previous* combatant's rendered frame for a frame or two before `Update()` re-rendered. Hiding never cleared the composition, which is exactly why hide-on-enter did nothing. The fix was to stop reusing: **close + recreate the card per appearance**, so it only ever composites the current content (fresh bars animate from zero, a clean intro). Lesson re-noted: a fix that doesn't work is data about a wrong model, not a reason to add a second fix on top.

## Placement as Alex's vision

Placement was where Alex stopped reacting and started *specifying*, and it was better than anything I'd have guessed. His vision: the popup's **bottom edge aligns to the hovered row's bottom edge**, content growing up, so the card reads as an extension of that row and tracks vertically as you move between rows. Then, mirroring the left/right flip: grow **up** by default, but if that runs off the top of the screen, grow **down** with the *first* row aligned instead. Plus a sharp catch — *"does the height of the popup header match the windows header height?"* (it didn't; now it does). The refinement that made it feel finished: align the last **row**, not the card's outer edge, to the hovered row — which required the card to report its chrome insets so the geometry could account for them. All of that generalized cleanly into the pure placement function the formalization later extracted.

## Formalizing: "this seems backwards"

Alex called the formalization scope precisely: *"can we simply brainstorm and implement the ui portion we have a spike for? No data being fed into it."* — the surface + the hover lifecycle, **placeholder content**, real data deferred to its own brainstorm. Clean separation, and it made the formalization small.

The architecture brainstorm is where I got corrected — twice — and the corrections are the keeper. I first framed it as "Core is the brain that owns rendering and its safeguards; the Plugin renderer asks Core for every decision." Alex: *"This seems backwards… what happens if we use a different renderer in the new plugin? we give that to core and pray?"* He was right. The reusable thing is the **UI component**, not Core-as-driver. Core is a library of **pure functions** (placement geometry + the off-screen safeguard) that a component *calls*; Core never calls out, never knows a renderer exists; the dependency points one way, Plugin→Core. And WPF literally **cannot** live in Core (`netstandard2.0`), so the shared UI toolkit lives in the one Plugin DLL — which every module already shares. His real north star surfaced here: *"i want to be able to overhaul [the timers'] UI to use the nice row and multi window capabilities we set up via the meter"* — centralize the UI so the timer overhaul reuses the meter's components. The HoverCard is the first deliberately-shared citizen of that toolkit; the geometry is the genuinely-reusable, testable part that lands in Core now.

That reframe also forced an honest reconciliation with the spec's convergence guardrail (single-consumer forms stay module-only; don't pre-generalize for imagined consumers). The HoverCard has one real consumer — the meter. So "module-agnostic" had to mean **not hardcoding the meter** (free, since the card is parameterized by style + content anyway), **not building unused timer features**. Stated that way, the ceiling holds, and I put it in the spec so a reviewer wouldn't have to wonder.

## Spec + plan, reviewed to closure

Both went through the automated third-party loop, two rounds each, and both r1 findings were mine to own. The spec's: my rework of the drill-down subsection **retitled a bold `Reserved seams` label** that five `§Reserved seams` cross-references pointed at — I'd dangled three of them in my own new text. Fixed by restoring the anchor. The plan's: I'd documented `VisualStyle` as `Eq2Auras.Core.Config` when it lives in `Eq2Auras.Plugin.Overlay`, carrying a dead `using` — a spike copy-over. Both verified against the tree before fixing (receiving-code-review), both closed clean. Alex also asked, pointedly, for **every variance** between the design I'd verbalized and the spec I wrote; the two real ones were that "delete the async channel" was a non-op (we built fresh off `main`, which never had the spike code) and that the spec *added* the guardrail reconciliation. He called them *"an effort to keep the spec sane."*

## Shipping — and the version-number quirk

Implemented inline: Core `HoverPlacement` under strict TDD (9 branch tests, Core **274 green**), the module-agnostic `HoverCard` (transcribed from the field-proven spike surface, renamed, `ShowAt` delegating to Core), and the meter's hover lifecycle fed `PlaceholderRows()`. The formalization is notably *smaller* than the spike: **synchronous placeholder means no data channel at all** — `OverlayHost`, `EncounterProbe`, the callbacks, the plugin wiring are all untouched (the spike's parallel async channel simply wasn't ported). Branch CI compiled the WPF, then merged `--no-ff` to `main` → `dev-latest 1.1.38`.

The quirk to remember: **1.1.38 is a lower number than the spike's 1.1.40**, because the spike's `.31`–`.40` were manual release *renames* that never advanced `main`'s commit count, and the version is `git rev-list --count` since the `version.txt` bump. It looks like a downgrade and isn't. It works only because the updater is identity-based (`1.1.38 ≠ 1.1.40` → pull) — verified in `UpdateDecision.cs` before pushing. From here `main` is the source of truth again; the manual-publish era is over.

## Where it stands

`dev-latest 1.1.38` (the formalized hover surface, placeholder-fed), `stable 1.1.0`. Both `hover-card` and the superseded `mouseover-spike` are deleted, local and remote — only `main` remains. **Next session: brainstorm the real data pipeline** for the hover states across the meter's various metrics — the single seam is `MeterWindow.PlaceholderRows()`, the crux is the per-`(metric × level)` grouping key (Victim for outgoing, Attacker/source for incoming, …), and — per the rule that started this whole session — it's a **blank page**. After that, the timer-UI overhaul onto the shared toolkit this pass established.

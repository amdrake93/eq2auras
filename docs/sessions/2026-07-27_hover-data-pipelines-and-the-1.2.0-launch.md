# Session chronicle — hover data pipelines, two field bugs, and the 1.2.0 launch

*2026-07-26 → 27. Picking up the spike-to-formalize handoff: the hover surface had shipped placeholder-fed, and the one open seam was `MeterWindow.PlaceholderRows()`. This session fed it — twice — and shipped the whole hover arc to **stable 1.2.0**. Two data pipelines (by-counterpart across the seven scalar metrics; the recap-second event log), two field bugs the Mac couldn't see (a latency reversal; a clipping bug only a screenshot could crack), a MINOR-bump launch, and a reckoning where the repo's living docs had quietly outgrown their own memory. Stories worth keeping: how one rule covered seven metrics; the design premise the field falsified; "why not just always update it?"; the contradiction only a screenshot resolved; a reviewer finding I was right to refuse; and memory-as-shadow.*

## One rule, seven metrics

The by-counterpart brainstorm's keeper was the unifying frame: a hover shows **this row's number broken down by its counterpart**, and the counterpart flips with the metric's direction — an outgoing metric groups by the swing's **Victim** (what I hit / healed / cured / fed), an incoming one by the **Attacker** (who hit / healed me). That direction isn't new config; it falls out of the `breakdownSource` descriptor each metric already carried for the by-ability drill (the two `Incoming*` sources → attacker, everything else → victim). So one rule covered all seven scalar metrics and both scopes — and it matched Alex's own per-metric phrasing case for case (DPS = what did I hit, Damage Taken = who hit me, Enemy Healing Done = whom did that mob heal). The pipeline was mostly **reuse**: the drill's request→read→rank channel generalized with a `ByAbility | ByCounterpart` grouping discriminator; the only new Core was a pure `IsIncoming` rule, the only new Plugin a granularity-agnostic swing-grouping helper. Full-autonomous end to end — spec and plan each third-party-reviewed to closure, implemented inline, merged, dev-latest.

## The premise the field falsified

Then the field bit. "It has a strange lag even outside of combat." Under systematic-debugging — unreproducible on the Mac, so an AskUserQuestion localized it to "the card appears late." The root cause was **my** design: I'd built the by-counterpart hover poll-driven, the card painting only once the reading landed (≤300 ms), reasoning "a mouseover is a deliberate act, ≤300 ms is fine." The field said no — that delay plus my hide-on-row-switch read as lag. The premise was mine, and the box killed it.

Alex's counter was the good part: *"since we're constantly updating the buckets, is it much cost to just have this data updating at our same rate as the rest of the row stuff?"* — why not precompute for everyone so any hover is instant? The answer is the whole reason the design went on-demand: the main rows read ACT's cached totals (O(1)); the by-counterpart read iterates raw swings grouped by counterpart, **per combatant**. Doing that for all 24 raiders every poll is exactly the per-combatant fan-out the engine doc warns off. A synchronous read of the **one** combatant the cursor actually landed on gets the same instant result for 1/N the cost. Approach A. On enter, the window now reads under the lock and paints at once; the poll keeps it live. A subtlety fell out of it: the poll path used to hide the card whenever a reading was momentarily missing, which would flicker the just-painted card on a one-tick race — so it now **keeps** the sync-painted card and hides only when the combatant genuinely leaves the list (a proper auto-exit, better than what had shipped).

## "Part III, not Part I"

Small but worth keeping. The latency fix-flow's reviewer raised a Minor: my probe comments cited "SPEC Part III §Row drill-down — the by-row mouseover," and it argued that should be Part I. I checked before touching it — §Row drill-down **is** Part III; §The hover surface (the UI card) is Part I, and it explicitly routes the mouseover *data path* out to Part III. The citation was correct; changing it would have introduced the error. I pushed back with the part headings and SPEC:79/:427 as evidence, and the reviewer re-verified and conceded — "my finding conflated the two." receiving-code-review cuts both ways: the loop is only worth anything if the writer disputes wrong findings as rigorously as it fixes right ones.

## Different data, same pipes

The recap-second hover was Alex's chosen stable marker — "wraps up hover for the basics and the current exception." The brainstorm's fork: a hovered recap second could show its events **grouped by source** (ranked, reuse the breakdown engine) or as a **chronological event log** (each swing its own row). Alex picked the log — "the damage events and heal events" — and that reshaped the data path. A per-event narrative isn't a ranked contribution, so it earned its own small Core builder (`RecapSecondEngine`, a sibling to `DeathRecapEngine`, itself already deliberately-not-the-breakdown-engine). The old reserved-seam prose had *guessed* "fed through the breakdown engine" — wrong once the shape was a log; I corrected the spec.

A clarification saved a wrong build. Alex said he wanted "the target that did the event" too — but a recap is the victim's *incoming* stream, so the target is always the victim (already in the header); he meant the **source/actor**, which the `Source · Ability` row already carried. And the keeper realization: a past second's events are **historical and immutable**, so — unlike the by-counterpart hover — this needs no poll-refresh channel at all. One synchronous read on enter, static until you leave. Simpler than the thing it followed. "Different data into the same pipes," as Alex framed it: reused `HoverCard`, `HoverPlacement`, the `ReadHoverNow` seam, unchanged.

## The contradiction only a screenshot could resolve

Second field bug: "the abbreviations dont show the letter." systematic-debugging again. The Core formatter was provably correct — tests assert `SignedAbbreviate(-5000) == "-5K"` — so the letter *was* in the string; a rendering problem. But the number columns are **right-aligned**, and a right-aligned overflow clips the **left** (the sign), which should keep the rightmost letter. That flatly contradicted "the letter is missing," and I couldn't reconcile it from the code. So I didn't guess a fix — I asked for a concrete example, and Alex sent a screenshot. Unambiguous: `-1.89`, `-1.06` — six-character signed abbreviations losing their `K`, while sub-1000 values (`-825`, `-498`) rendered fine. Root cause: the columns reserve width for the unsigned worst case `9.99M` (five chars); a signed `-1.06K` is six, and the extra sign pushes the `K` past the cell edge. **Latent in the Death Recap since it shipped (1.1.29)** — earlier field tests never hit ≥1K per-second nets — and the hover surfaced it. One-const fix (`9.99M` → `-9.99M`), fixing both surfaces since they share the reserve. Re-noted lesson: when the static analysis and the symptom contradict each other, that's the cue to gather evidence, not to patch.

## 1.2.0

All four field checks approved, so: the launch. A direct `version.txt` 1.1→1.2 commit built `dev-latest` 1.2.0; the promote workflow shipped the **exact bytes** to `stable` 1.2.0 (Alex OK'd byte-identical, waived the pull-glance). Second MINOR bump — the 1.1.x line closes, as 1.0.x closed at 1.1.0 for the drill-down. Both channels 1.2.0; the public now rides the whole hover arc: surface + by-counterpart + latency fix + recap-second + the width fix. Four merged branches deleted; only `main` remains.

## Memory as shadow

The last beat was Alex's, and it was a sharp catch: *"do we need to handle this memory? we've been chronicling every session as well as a rather exhaustive list of plans that implement the existing, living documentation, spec."* The repo had matured into a real living-docs stack — SPEC as source of truth, backlog as queue + status, `sessions/` as the why, `plans/` as task-records, `review-workflow.md` + CLAUDE.md as the process — and the **memory store had quietly become a second changelog shadowing it**. `active-direction.md` was a screen of shipped detail already in the backlog and git; half the working-style files re-hosted `review-workflow.md`/CLAUDE.md near-verbatim. The audit found **no divergence** (memory matched the repo) — just duplication, which is its own rot: drift risk plus dead weight loaded every session. 12 memories → 6. Keep only what the repo *doesn't* hold — the `spike-data/` staging trap, "ground in cited references," "duplicate = whole pipeline," the mode taxonomy, the ACT decompile command — and slim `active-direction` to the one thing memory is actually for now: current channel versions plus a single **Next item** slot, empty unless Alex has named it. The rule that fell out: *memory holds what the living docs can't, and nothing they already do.*

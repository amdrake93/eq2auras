# Session chronicle — a wiki generated from the SPEC, and the debt the projection mirrored back

*2026-08-10 → 08-19. One very long session with a clear spine: build the player-facing docs the project has owed since 1.0 — but build them as a **generated projection of the SPEC**, not a hand-maintained wiki that rots the moment a feature moves. That meant authoring a repo-scoped `generate-user-docs` skill the writing-skills way (empirical RED/GREEN, not prose), running it for real, and defending it through an independent review. Two smaller threads bookended it: a doc-cleanup opener, and a frozen-tag bug the plan review flushed out. The through-line, in hindsight: a faithful projection reflects its source's flaws straight back at you — and an empirically-built tool shouldn't be patched on an abstract argument.*

## Part I — the openers, and a tag that had been frozen since July

We started in the backlog: trimmed stale `1.0.0`/`0.1.x` cutover narrative from SPEC §Versioning, dropped two dead bugs, shipped it as a doc-only `dev-latest 1.4.15`. Then the housekeeping from the prior session's review-skill work — scrapping `docs/review-workflow.md` and pointing `CLAUDE.md` at the user-scoped `requesting-design-review` skill, retiring two over-formalized review types that were never meant to be first-class. Merged `[skip ci]`.

The interesting one surfaced *sideways*. While reviewing the user-docs **plan**, the reviewer's provenance check found the `dev-latest` git **tag** frozen at `6c5e680` (2026-07-14). `softprops/action-gh-release` refreshes the *release* and DLL asset on every push but never re-points an existing tag — so `promote.yml`, which reads a promoted build's source commit from that ref, had stamped **`v1.4.0` onto the wrong pre-meter commit**. Field-harmless (the shipped DLL and version name were right), but the `vX.Y.Z`→source-commit spine — the whole revert/rebuild story — was pointing at the wrong place. Fix in two parts: `build.yml` now force-moves the tag to HEAD on each `main` publish (`gh api PATCH … || POST`), and we re-pointed `v1.4.0` to the true source `2693c1d`. One straggler the fix-flow review caught: the step first ran under **pwsh** and broke on bash `\`-continuation — it needed `shell: bash`. Reviewed to closure, merged; `dev-latest` walked out to **1.4.22** across the arc.

## Part II — teaching the skill, and the moment we caught ourselves faking TDD

The design was settled quickly: the GitHub **wiki** becomes the player-facing feature layer, **generated from the SPEC read at the promoted `vX.Y.Z` commit** (never live `main`, so docs describe the bytes players run), text-only, via a repo-scoped skill; regenerate at stable promotion, maintainer-run. The honest work was the skill itself, and here Alex asked the question that redirected the whole afternoon: *"are we actually using the writing-skills skill, or did our plan just replicate it?"*

We were replicating it. The plan *described* a TDD-shaped process without ever running the RED baseline. So we actually ran it — and it earned its keep twice:

- **The voice guard.** The first cut used a *prohibition* list ("don't sell, no 'at a glance'"). Under the competing pressure to be exhaustive, reps leaked a mild sales flourish anyway — and the specific tell, "at a glance," turned out to be **the SPEC's own phrasing**; the agents were being *faithful*, not salesy. Recast as a positive contract ("open with what a thing **is**") plus an outright ban on that one phrase, it bound 3/3.
- **The fidelity guard — the one that mattered.** Testing the Class-colours section, reps **fabricated a full subclass→colour table** (2/2) that does not exist in the SPEC (the palette lives in a plan doc + Core source; the SPEC names `SubclassColors` and lists nothing). The "be exhaustive" depth rule, handed a table structure, invented data to fill it. We added a fidelity contract — *every concrete value traces to the source; a set the source names but doesn't enumerate is described, not invented* — and it bound 3/3: "each subclass has its own fixed colour," the real grey `#8B93A3` kept, no table. Alex's call: keep the skill **strict to the SPEC**; he'll backfill the palette into the SPEC rather than teach the generator to reach outside it.

The exemplars themselves took several rounds of blunt feedback — "this is a sales pitch," "too thin, I expected exhaustive," "too much in one sentence, sections are fine" — before landing as neutral, fully-enumerated, granular reference prose built against the *actual* v1.4.0 SPEC. One mechanical trap: `.claude/` is fully git-ignored, so the skill was invisible to git until a stepwise re-include exception (`\.claude/*` → `!…/skills/` → …) let just that one skill ship.

## Part III — the first generation, and the projection as a mirror

Running it for real: read the v1.4.0 SPEC, slice per-page **source bundles** of only the mapped sections (fidelity by construction), dispatch one generator per page — Timer-Overlay from 13 sections, Parse-Meter from 6 — then assemble Home/Sidebar/`.generated-from`, verify every concrete value against source, and push live over SSH to the wiki's `master`. Both pages checked out clean: the example names (`Aeralik`, `Cleaving Strike 9.8K`), the hex codes, the "last 10 seconds" recap window — all traced to the SPEC.

Then Alex looked at the 4,700-word Parse-Meter page and said the quiet part: *"some of this could get its own sections instead of being ridiculously long."* The diagnosis is the session's best line: the page is long because it **faithfully projects an under-decomposed SPEC**. §The meter window is one ~2,000-word catch-all — the meter accreted across slices and grew a fat section instead of decomposing as it went. The generator did its job; it made the SPEC's own organizational debt *visible*. So the fix isn't a manifest hack — it's upstream, in the SPEC, and once the sections are split the multi-page wiki falls out for free. Captured as a backlog item (with the palette-gap folded in): a deliberate **SPEC-reorganization** effort, direction-set, not started.

## Part IV — the review, and refusing to patch an empirically-built tool

Alex wanted an independent review of the skill, but pre-loaded a sharp caution: *pause on any feedback* — a reviewer reasoning **abstractly** about a skill it can't rep-test is weaker evidence than the reps that built it. The Fable-5 reviewer did real ground-truth work (re-resolved all 19 manifest prefixes at three tags, verified the tag model and both golden examples) and returned 2 Important + 4 Minor + 1 Nit.

The reframe that made the caution precise: **almost every finding was about operational mechanics** — the incremental-regen hash, an undefined multi-match case, a wrong git-fact, doc consistency — a surface the reps never exercised, and where the reviewer was genuinely useful. Two were real gaps (the `.generated-from` marker hashed the manifest but not the style guide; prefix resolution had no defined multi-match behavior). We applied six. The **one** finding in rep-tested territory — the Escalation exemplar's "nothing to configure" vs. the `EscalationStyle` knob — was exactly the abstract case: the *actual generated page* documented both modes correctly, so the exemplar hadn't misled anything. We tightened it anyway; round 2 said the reword was surface-only, the mechanism list still Center-radial-framed.

And here Alex drew the line, correctly: **review done, skill unchanged.** Editing a golden exemplar is changing generation-shaping guidance, and writing-skills' Iron Law is "no skill change without a failing test first." There is no RED here — we never watched the exemplar cause a bad generation; we watched the opposite. Patching it to satisfy an abstract prediction is precisely the move the pipeline exists to prevent. If it ever genuinely needs revisiting, it goes back through writing-skills, not a reviewer-driven edit. Recorded as a no-change so a future review can't re-litigate it. Merged `[skip ci]` (doc + skill only, DLL untouched) → `main` at `86b9e74`.

## The through-line

Two lessons worth keeping. First: **a generated projection is a mirror** — the wiki didn't invent the meter's bloat or the missing palette, it reflected the SPEC's own state, which is a feature, not a bug (it turned latent doc-debt into a triaged item). Second: **the discipline that builds a thing defines how you're allowed to change it.** The mechanics the reps never tested were fair game for the reviewer and we fixed them; the generation behavior the reps *did* bind is only touchable through the same empirical loop. Knowing which half a finding lands in was the whole skill of the review.

**Open threads:** the SPEC reorganization (meter section split + palette backfill) — its own effort, not started; the live wiki's `.generated-from` still carries the pre-review marker format (harmless — next run fail-safes to `--full`); and the standing queue — raid buff tracker + timer-framework refactor, the class-name row label, poll-health observability.
